# SEO, AI SEO/GEO and programmatic SEO audit

Audited 2026-11-12 at implementation commit `d7fae2c` using the installed
`seo-audit`, `ai-seo` and `programmatic-seo` skills. This is an audit, not an
implementation or deployment change.

## Assessment

Home and Work have a sound crawlable foundation, with readable content, accurate
identity/contribution text, JSON-LD and working social images. The implementation
is **not ready for the custom-domain cutover**: none of the sixteen legacy article
URLs resolve, the Journal is an empty migration notice, and release/indexing and
discovery controls remain unfinished. These are mainly planned backlog work,
not regressions in the completed Work gallery.

The best next investment is preserving existing writing and publishing the three
evidence-led project stories. Mass-producing keyword variants would add little
value to this personal portfolio.

## Scope and evidence

- Inspected source, configuration, existing tests, approved blog design and
  `origin/old` without switching branches. No product-marketing context file was
  found in the current checkout; existing project/content documents supplied the
  audience, identity and migration context.
- Inspected thirteen routes in Chromium with JavaScript disabled against the
  existing production build on `http://127.0.0.1:3109`. Captured actual DOM metadata,
  JSON-LD, headings, content, media attributes and links. Structured-data findings
  are based on browser DOM and source, not a script-stripping web fetch.
- Checked all sixteen dated article URLs derived from the old article index,
  eighteen unique root-relative link destinations found on current 200 pages,
  and both distinct social-image URL forms.
- Requested Work HTML with Googlebot, OAI-SearchBot, PerplexityBot and
  Claude-SearchBot user-agent strings. These are local application checks, not
  proof that provider IPs pass a deployed CDN/WAF.
- Machine-readable observations: [audit evidence](2026-11-12-evidence.json).
  Localhost absolute URLs are intentional in this test build; they are not
  evidence that the live site emits localhost canonicals.

No Search Console, Bing Webmaster Tools, GA4 reports, field Core Web Vitals,
backlink data or repeated AI-answer measurements were inspected. The custom
domain still serves the old implementation per the owner. This report makes no
claim about its current rankings, traffic, indexing or AI citations. It does not
establish live Netlify headers, TLS, redirects, robots rules or bot protection.

## What already works

- All six content routes are accessible without JavaScript and have one H1,
  unique document titles and descriptions, except `/experience`'s generic
  inherited description. Contact, CV and primary navigation are real links.
- Eighteen tested root-relative link destinations return 200. The sampled unknown
  path returns a real 404 with noindex, rather than an SPA soft 404.
- Home's identity, Adobe role and external identity links agree with visible
  content. Work's eleven-entry structured index reflects visible contributions,
  status and real destinations, without invented ratings or outcomes.
- Archived work is labelled; unfinished/unavailable destinations are not fake
  links. Community co-authorship is explicit. Source-derived diagrams and real
  image outputs have readable captions and attribution.
- Both social-image URL forms return `image/png` with actual 1200×630 dimensions.
  No missing-OG-image issue was reproduced on the current build.
- Home/Work image elements inspected in the no-script DOM have alt text and
  intrinsic dimensions. Below-the-fold gallery images are lazy-loaded. Existing
  responsive, native-scroll and reduced-motion browser tests support the mobile
  baseline; field performance and all-browser accessibility are not inferred.
- Four tested crawler user-agent strings receive Work's index, archived status,
  JSON-LD and OG image metadata in initial HTML with status 200 locally.

## AI SEO/GEO plan

Prioritize useful, attributable source material over AI-specific formatting:

1. Put complete technical answers on the migrated article and case-study routes.
   Each should state what was built, Miki's contribution, relevant constraints,
   decisions and supported evidence in ordinary headings and paragraphs.
2. Keep one source of truth for names, roles, dates, project lifecycle and URLs.
   Use shared records for HTML, schema, discovery and optional machine-readable
   summaries. Never update publication dates merely to suggest freshness.
3. Declare crawler controls by purpose. Search discovery and training controls
   are distinct: OpenAI documents OAI-SearchBot separately from GPTBot and
   user-triggered retrieval. Do not introduce a narrow named-bot allowlist that
   accidentally overrides the wildcard policy. Verify deployed WAF behavior.
4. Use plain author/contact information and existing authentic GitHub, LinkedIn,
   Schrödinger Hat and publication links. No Wikipedia/review-site campaign is
   justified by this audit; their presence or quality was not measured.
5. After launch, establish a small prompt baseline such as “Who is Miki Lombardi?”,
   “Who created ImageGoNord?”, and “How was the supermarket waiting-times service
   built?”. Add topical article queries only when their content is published.
   Repeat each across selected engines and record dates, sample counts, answer
   accuracy, citations and cited URL. One response is not a visibility metric.

Google explicitly says its AI search features require no special markup or
AI text files beyond normal SEO eligibility. Schema should match visible content.
Treat optional emerging files and third-party vendor statistics as experiments,
not requirements or forecasts. Do not turn ordinary sections into forced 40–60
word fragments or add irrelevant FAQs merely for extraction.

## Programmatic SEO assessment and template contract

**Appropriate scale:** sixteen known legacy articles, three evidence-backed
featured stories and the existing eleven-entry hub. No search-volume or ranking
data was supplied, so no traffic estimate or broader keyword opportunity is
asserted. The inventory's short records are not enough to justify eleven new
detail pages on their own.

| Template | URL and title | Content requirement | Metadata / schema | Linking and publication gate |
| --- | --- | --- | --- | --- |
| Article | Preserve `/blog/<date>-<permalink>`; real original title plus site name | Complete original body, summary, author, original date, source/media/code, honest substantive updates | Unique description and canonical; Article/BlogPosting with visible supported facts; specific share image plus fallback | Journal hub, contextual related links and return link; published-only sitemap/RSS; drafts/future posts excluded; unknown slug 404 |
| Project story | Use the route selected by MIC-16, e.g. `/work/<slug>`; project name plus specific story angle | Individual/team role, problem, constraints, alternatives, decisions, evidence and lessons; authentic credited media | Unique canonical/description/social card; only appropriate CreativeWork/SoftwareSourceCode facts where supported | Work hub → story → source/demo/related story; publish only when evidence makes the page useful; no empty detail routes |
| Index/hub | `/work`, `/blog` | Real summaries and useful organization; no near-identical tag/filter pages | Canonical base or deliberate distinct pagination strategy; structured lists consistent with visible items | Every published detail page reachable by links; avoid indexable query permutations or orphan pages |

Reuse the current Next.js Server Component/data approach. No new SEO framework,
database or page-generation dependency is justified. Keep route slugs unique,
validate frontmatter, and generate navigation/discovery from the same records.
Do not create technology × project, city, persona, comparison or translation
permutations without distinct useful content and validated audience demand.
English shell content does not justify hreflang; preserve the Italian article's
language accurately when migrating, without inventing translated equivalents.

## Release verification and measurement

Before cutover:

1. Preserve all sixteen article routes, the known date alias, raw Markdown/media,
   `/whoami` mapping and CV using a checked-in migration manifest and tests.
2. Test release origin and index/noindex modes, actual hosted responses, canonical
   domain variants and deliberate permanent redirects without chains.
3. Verify sitemap/feed syntax and canonical published-only contents; check every
   listed route. Confirm no unpublished records leak through raw files or APIs.
4. Inspect rendered metadata/schema on Home, Work, About, article, project and
   longest-title/missing-art cases. Validate eligible schema with official tools;
   syntactically parsed JSON alone is not a rich-results validation.
5. Measure mobile production performance with a lab tool, then use field
   LCP/INP/CLS when sufficient live data exists. Local load times are not a field
   Core Web Vitals verdict. Inspect CDN/cache/TLS and bot access on the actual host.

After launch: compare Search Console indexed/expected URLs, crawl errors,
queries/clicks and canonical selection; submit the sitemap and inspect migration
URLs. Keep GA4 preview traffic excluded, track useful contact/CV/newsletter
actions, and separately record repeatable AI-answer accuracy/citation observations.
Search Console aggregates Google's AI-feature traffic into normal Web reporting;
this audit does not claim a separate AI visibility dashboard or citation lift.
